## Standalone editing versus ATW read-only integration

The standalone surface is a small Java reader/editor: it exposes `PUT /fs/file`, Monaco dirty state, save retry, `didChange` and `didSave`. The embedded ATW fixture deliberately reuses the same UI source but sets `readOnly: true`, disables `onChange`/`onSave`, and uses the Gateway read-only LSP boundary. Therefore a standalone smoke proving save must not be reused as evidence that the ATW code canvas can modify the checkout. Conversely, the embedded canvas can still send document synchronization and use definition/references/completion; those are in-memory LSP operations and do not prove disk writes.

The two surfaces also differ in deployment: standalone app configuration accepts a Gateway URL/token/root form, while the embedded path obtains a bootstrap session from its host. The fixture's embedded code is therefore the relevant surface for an ATW requirement discussion; its copied standalone controls are not exposed through the host integration.

## What this means for a requirements fixture

The strongest current Java sample is: open a real Maven project, show project/module/JDK metadata, search files/text, open Java, wait for jdtls indexing, go to definition, find usages, and request member completion while preserving a read-only buffer. A requirement that says “edit, save, refactor, format, run tests, debug, or reproduce the exact historical Run version” crosses the current fixture boundary and needs an explicit new capability plus evidence. The source currently has no code revision/content hash check for a historical Run; it resolves a workspace/ref and reads its current files.
