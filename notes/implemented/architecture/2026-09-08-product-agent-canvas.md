# 产品 Agent 画布复用知识库与正文阅读能力

Status: implemented

## 决策与理由

用户于 2026-09-08 确认“中间文档、右侧对话”和文档/全景切换，并要求沿用最新全局主题。实现复用知识正文、版本与来源；React Flow 只承担空间阅读。交互契约见[产品说明](../../../docs/product/product-agent-canvas.md)，选型过程见[调研报告](../../../docs/product/product-agent-canvas-research.md)。

正文、来源和生效状态继续由已有知识服务维护。新增 owner 查询只收窄集合，不扩大 requester 的读取权限。空间坐标是展示数据，不赋予知识发布权限。引用把工作区、Agent、条目与确切版本随用户消息送入现有 Chat；发送后显示为可展开的引用卡，传输元数据不挤占聊天正文。

`role=pm` 只决定默认打开画布的展示偏好，当前对应 Nova；其他普通 Agent 可以显式打开画布，偏好按稳定 Agent ID 隔离。系统身份与知识读取权限仍由原有服务端规则决定。视觉使用全局中性表面、蓝色操作色与无衬线字体，不移植草图中的水墨配色。

## 放弃了什么

- 将 `diagram-design` 直接当作画布 SDK：它提供图表生成技能与模板，不能覆盖应用布局、知识范围、版本和持久化。
- 为了阅读 PRD 就整体引入另一套文档工作台：现有正文读取已经存在，先证明混合编辑或协作需求再承担内容模型迁移。
- 把聊天中的“已更新”或图形编辑器的本地 JSON 作为知识库的新权威：会使已发布版本、来源和权限出现分歧。

## 复活条件

- 用户明确需要手绘、自由图形与便签 → 对 Excalidraw 做真实嵌入验证 → 场景 JSON 与知识引用分离，保存经过服务端校验。
- 用户明确需要任意富对象在无限画布中混排，且取得适用的 tldraw 生产授权 → 比较自定义对象与完整文档阅读的成本 → 先验证 React 版本兼容及内容生命周期。
- 用户明确需要多人实时块编辑及文档/白板双向互转 → 重新评估 BlockSuite 等编辑框架 → 先制定知识正文、编辑文档状态和发布版本之间的单一权威链。

知识页面保持只读，文档编辑和发布继续经知识管理员。验收只在数据库副本与专用样本上进行，没有修改原知识库。用户已明确授权合入 main；验收副本与构建保全到主树的 Git 忽略目录，具体记录见[验收说明](../../../docs/product/product-agent-canvas-acceptance.md)。
