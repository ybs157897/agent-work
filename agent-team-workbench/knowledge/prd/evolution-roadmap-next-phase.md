## 3. PHASE 1（0-2 周）：关闸门

### 目标

## 6. 关键决策记录

### 6.1 到货通知形态

**决策**：先浮标后通知中心。不建独立通知面板，在看板/任务列表使用 badge 和浮标。等用户验证了通知的消费频次和转化率，再决定是否扩展为独立通知系统。

**理由**：侵入小，1 天可落地。用户当前主要交互面是看板，通知在关注点附近出现比在独立面板中出现更有效。

### 6.2 `application` 包拆分时机

**决策**：PHASE 2 同步做，不推迟到 PHASE 3。架构耦合评审已标注为 P0——当前 Service 是 4928 行的 God 对象，每次新功能都改它，不改拆分的代价是每轮迭代的摩擦成本。

**风险**：拆分期间新增功能受阻。缓解措施：拆分期间只修 bug 不增功能，配合 Feature Flag 隔离。

### 6.3 Agent 招聘 vs 看板主循环优先级

**决策**：看板主循环体验（到货通知/验收摘要/自动起跑）优先于画框/recruit。用户已定调「现阶段唯一焦点是把既有 agent 的能力做扎实」。分界线：看板三缺口补齐 + 产品 Agent 自维护回路验证通过后，才启动 recruit 实现。

### 6.4 前端技术栈收敛

**决策**：不引入 Ant Design 或其他组件库。当前 Aceternity UI + 自主 Ink Design System 的路线已经验证了可维护性，且 ANTd 的引入会增加包体积和样式冲突风险。仅借 Ant Design X 的交互范式（ThoughtChain/Bubble/RICH）作为设计参考，不依赖其实现。

### 6.5 真实身份认证 MVP 范围

**决策**：最小 MVP 只做 JWT + 本地用户表，不依赖外部 IdP。PHASE 3 在需要多工作区时再考虑 OIDC/OAuth2 集成。

## 8. 风险与缓解

### 8.1 高影响风险

| 风险 | 影响 | 概率 | 缓解 |
|------|------|------|------|
| CI 建立后现有测试在 CI 环境失败 | PHASE 1 延后 1-2 天 | 中 | 先本地模拟 CI 环境跑全量，预判失败点 |
| 真实身份认证设计复杂度超预期 | PHASE 1 延后 1 周 | 中 | 最小 MVP：JWT + 本地用户表，不依赖外部 IdP |
| `application` 拆分期间新增功能受阻 | PHASE 2 交付延迟 | 高 | 拆分期间只修 bug 不增功能，配合 Feature Flag 隔离 |
| 产品 Agent 首轮自维护 loop 产出质量低 | 用户信心下降 | 中 | 首轮人审 + 调整 prompt，逐步放开自动化 |
| Codex app-server 协议升级漂移 | 升级时适配成本高 | 中 | 按 reference 文档的升级同步规程重算 schema SHA |

### 8.2 待验证假设

1. **目标用户愿意从 IDE/CLI 切换到 Workbench**：未验证留存和使用频次。建议在 PHASE 2 埋点后收集 2 周数据，再决策是否加大投入。
2. **Lead/Worker 编排能降低总交付时间**：需 A/B 对比单人单 Agent 与多 Agent 编排的实际耗时和质量。建议在 PHASE 2 产品指标埋点就绪后，设计一次对照实验。
3. **审批不会成为主要阻塞点**：需统计审批等待时长、拒绝率和超时率。建议在 PHASE 2 错误分类文案中直接埋入审批等待时长统计。
4. **用户理解当前概念模型**：建议对 5 名目标用户做首次成功路径测试，在 PHASE 2 向导设计前完成。
5. **SQLite 本地模式可以平滑迁到 PostgreSQL 团队模式**：需一次真实迁移演练和并发压测，建议在 PHASE 3 多用户改造前完成。
6. **产品 Agent 的定时梳理产出对用户有价值**：首轮跑完即验证，建议在 PHASE 2 首航后立即收集用户反馈。
