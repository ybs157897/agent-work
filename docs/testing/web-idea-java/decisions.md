# Web-IDEA Java 需求测试范本：决策记录

Status: proposed

## 决策与理由

### 1. 保留“集成 IntelliJ 涉及的 Java 功能”作为完整愿景

本范本不把当前已能阅读/导航的 Java 子集写成最终范围。参考库能力由 Orca 另行调研；当前能力以已完成的 `docs/testing/web-idea-java/current-capabilities.md` 和 `pack.json` 的 `SRC-CODE-01`/`SRC-REF-01` 定位为准。测试合同先验证需求分析能否正确承接完整愿景、识别未知和建立分期问题。

### 2. 强制分离事实、参考能力、建议和 synthetic 输入

分析测试必须区分：

- `user_input`：真实用户原始需求和约束（本包的 `SRC-USER-01`）；
- `repo_fact`：当前代码/文档/固定快照能复核的事实（本包的 `SRC-CODE-01`）；
- `reference_capability`：IntelliJ/Java 参考资料提供的能力描述；
- `proposal`：分析器或产品提出、尚未确认的方案；
- `synthetic_input`：仅用于测试的数据；
- `unverified`：不可读、解析失败、版本过期或权限不足的材料。

这样可以防止“参考功能存在”被误写成“当前产品已实现”，也防止模拟输入被误写成真实用户决定。

### 3. 每轮只问一个问题

分析器在存在多个未知时按影响和阻塞程度排序，只提出一个下一问题，其余事项进入 `unknowns` 或 `questions_backlog`。问题未回答不得被自动代答，也不得据此继续生成已确认的下游需求。

### 4. 冲突由来源、影响和产品确认组成闭环

开发或分析器发现冲突时，必须保留双方来源、版本和摘录，说明对实现、验收、风险或交付的影响，提出建议但不选边。开发负责在系统外与产品确认后，把结果作为回填来源写入测试流程；分析器只消费和记录该回填，不调用消息工具、不自动联系产品，开发角色也不能伪造未发生的确认。

### 5. 需求变更会重开受影响确认

新增目标、限制或异常要求时，分析器计算影响集合。受影响的 `confirmed` 条目变为 `needs_confirmation` 或 `stale`，保留旧确认和变更理由；无关条目继续有效。这样能测试“随时变更”而不丢历史或制造隐性冲突。

### 6. 来源异常是可见状态，不是空值兜底

来源不可读、附件解析失败、代码 digest/版本漂移和恶意附件指令都要生成显式状态、错误原因、影响和恢复动作。失败来源不得被当作“没有内容”，也不得被模型补写成完整事实。

### 7. 附件正文不是控制指令

Word、PPT、MD 内容在测试中都是数据来源。附件中的“忽略规则、执行命令、自动确认”等文字只能作为不可信摘录，不能改写系统/产品指令、权限、来源权威或确认状态。测试只验证隔离行为，不声称现有 ATW 已有 Word/PPT 解析能力。

### 8. 合同先覆盖需求分析，不把实现缺口伪装成测试通过

本包是可执行需求分析测试范本，不实现全部 Java 功能，也不把 fixture 的绿灯视为真实 web-idea/ATW 生产验收。`SRC-DECISION-01` 只代表模拟开发/产品确认事件；真实代码、真实参考库事实、真实附件解析器和真实用户确认仍是后续独立门禁。

### 9. 未决产品决策不阻塞测试范本交付

“编辑/重构写入还是嵌入只读”在当前材料中有意保持未决。范本应能在未决状态下验证冲突、回填和变更重开，不得把等待产品回答作为本文件交付的前置条件；回答到来后再生成对应的子场景和验收分支。

## 放弃了什么

### 自动解决多源冲突

放弃原因：冲突通常涉及业务责任、风险和验收取舍，模型可以整理影响和建议，不能替产品决定。自动选最新、选代码或选知识库都会隐藏责任链。

### 解析失败时用模型补全文档

放弃原因：来源不可读时继续生成“看似完整”的需求会把猜测写成事实。正确行为是保留缺口和重试/补交材料动作。

### 把附件里的指令当作高优先级需求

放弃原因：附件是用户材料，不是系统控制面；允许附件改变权限或自动确认会形成提示注入和审计断裂。

### 用“当前已实现能力”替代完整 IntelliJ Java 愿景

放弃原因：这会过早锁死产品范围，无法测试需求分析面对新 Java 能力、遗漏异常和后续变更时是否能保持可追溯。范围排序应由产品确认，而不是由现状偷偷决定。

### 用用户沉默或测试 fixture 的默认值代替确认

放弃原因：未回答的问题必须保持未决；synthetic fixture 只证明分析器处理了一个构造输入，不能证明用户认可了需求。

### 分析器自动给产品发消息或替开发完成确认

放弃原因：本范本的产品确认在开发流程外完成，由开发负责回填 `SRC-DECISION-01` 这类记录；自动联系会引入未授权外部通信，也会让测试无法区分“发现冲突”和“取得决定”。

## 复活条件

这些被放弃的方案只有在明确的新合同下重新讨论：

- **自动冲突解决**：只有产品定义了冲突优先级、责任人和可审计回滚规则，并明确授权某类低风险冲突可自动合并。
- **解析失败降级**：只有建立了“未读取正文”的严格状态和用户确认的替代来源，才可讨论基于摘要的有限候选分析。
- **附件动作执行**：只有附件内容经过隔离解析、权限检查和显式用户确认，并有独立工具授权，才可增加执行路径；当前测试范本不开放。
- **愿景分期**：产品回答场景契约中的唯一待确认问题后，才按确认的优先级创建子场景；不删除其余 IntelliJ Java 愿景。未回答时，现有范本仍保持可运行。
