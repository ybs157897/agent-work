# 产品设计题：多 Agent 协作会话空间

## 题目

为 Agent Team Workbench (ATW) 设计一个「多 Agent 协作会话空间」功能，使得多个 Agent 并行执行子任务时，用户能在一个统一视图中看到所有进展、对比产出、识别冲突，并导出最终结论。

请完成以下 5 项工作：
1. **问题定义与用户分析** - 谁在用、场景是什么、当前断裂点在哪里
2. **竞品调研框架** - 列出 3 个调研方向/竞品，说明选择理由和核心调研问题
3. **功能定义** - 用户故事 + 验收标准（含边界条件）
4. **关键设计权衡** - 至少 3 组决策权衡，给出推荐及理由
5. **实施路线图** - NOW / NEXT / LATER 三阶段，含工期估算与 RICE 排序

## 自答

### 1. 问题定义与用户分析

#### 目标用户画像

| 用户类型 | 典型角色 | 核心诉求 |
|---|---|---|
| P1 - 技术负责人 | 团队 leader、架构师 | 需要看到多个 Agent 协作的全貌，做决策判断 |
| P2 - 高级开发者 | 主力贡献者 | 并行派发子任务，需要聚合结果而非手动拼接 |
| P3 - 质量/测试人员 | QA 工程师 | 验证多个 Agent 产出的交叉影响，识别冲突 |

#### 核心场景

**场景 A：分解式开发（P1 + P2）**
> 作为技术负责人，我向一个 Coordinator Agent 描述需求，它自动分解为多个子任务派发给不同 Specialist Agent，我希望看到各子任务的进展、依赖关系和最终汇编结果，以便在合并前发现冲突。

**场景 B：多视角代码审查（P2 + P3）**
> 作为开发者，我同时派发两个 Agent 分别做「安全审计」和「性能优化建议」，我希望在一个视图中对比两套建议的交叉影响，避免一方修复带来另一方的新问题。

**场景 C：竞争性探索（P1）**
> 作为架构师，我给两个 Agent 同一道开放性问题（如"选型 A 还是 B"），让它们分别独立调研后给出结论。我希望在同一个画布上看到两套方案的论证链路对比，以便做出最终决策。

#### 当前工作流断裂点

```
当前：用户发起任务 → Agent A 执行 → 用户读结果 → 用户发起 Agent B → 用户手动对比
痛点：上下文切换成本高，对比维度不统一，结论依赖人工记忆
期望：用户发起任务 → 系统协调 → 并行执行 → 统一视图呈现
```

并行调研 3 个方向，每个方向委派一个子 agent，主 agent 汇总：

| 方向 | 具体竞品 | 调研焦点 | 选择理由 |
|---|---|---|---|

**核心调研问题（统一模板）**：
- 它们如何展示多 Agent 的并行产出？
- 有冲突检测机制吗？如何呈现冲突？
- 用户能否回溯单个 Agent 的完整推理链路？
- 评估技术实现复杂度 vs 用户体验质量

### 3. 功能定义

#### 用户故事

```
US-01: 作为用户，我可以在一个「协作空间」中看到所有 Agent 的实时进展，
以便了解整体任务状态而不需要逐个查看。

US-02: 作为用户，我可以按「任务分解树」或「时间线」两种视图查看协作空间，
以便在结构化和时序化之间自由切换。

US-03: 作为用户，我可以在协作空间中对不同 Agent 的输出进行标注和评论，
以便记录决策依据和交叉引用。

US-04: 作为用户，系统会自动检测不同 Agent 产出之间的冲突并高亮标记，
以便我快速定位需要人工介入的分歧点。

US-05: 作为用户，我可以将协作空间的最终产出以「报告」形式导出，
以便分享给未使用 ATW 的团队成员。
```

#### 验收标准

| # | 验收项 | 类型 | 可测性 |
|---|---|---|---|
| AC-01 | 协作空间在 Coordinator Agent 创建子任务时自动生成 | 正向 | 发起分解任务后自动跳转 |
| AC-02 | 空间内每个 Agent 有独立面板，显示当前状态（等待/执行中/完成/失败） | 正向 | 状态变化实时更新 ≤ 2s |
| AC-03 | 支持任务分解树视图，深度 ≥ 3 级时可折叠展开 | 正向 | 深度 ≥ 3 级时渲染正常 |
| AC-04 | 支持时间线视图，拖动时间滑块时面板内容同步更新 | 正向 | 滑块拖动时面板内容同步 |
| AC-05 | 冲突检测：系统自动比对两 Agent 产出中涉及同一文件/函数/变量的部分 | 边界 | 同一函数被不同 Agent 修改时高亮标注 |
| AC-06 | 冲突标注的误报率 ≤ 15%（可接受一定误报，不可漏报） | 边界 | 人工标注的 ground truth 自动比对 |
| AC-07 | 协作空间同时展示 ≥ 8 个 Agent 面板时不出现性能劣化 | 边界 | FPS ≥ 30，内存增量 ≤ 200MB |
| AC-08 | 导出报告包含所有 Agent 结论摘要与冲突标记，不含原始推理日志 | 边界 | 导出的 MD 文件可独立阅读 |

#### 技术要求与约束

- 实时性：WebSocket 推送 Agent 状态变更，延迟 ≤ 2s
- 持久化：协作空间是「会话」的一等公民实体，与 `task_sessions` 平级（只写墓碑，不 DELETE）
- Agent 输出按「事件流」模型存储，协作空间是事件流的聚合投影
- 前端：基于现有 React + pnpm 技术栈，不引入新框架
- 冲突检测：后端做语义 diff（AST 级别），前端只做渲染

### 4. 关键设计权衡

#### 权衡 1：实时同步 vs 最终一致性

| 方案 | 实时同步 | 最终一致性（推荐混合） |
|---|---|---|
| 描述 | Agent 每产生一个 token 就推送到空间 | Agent 完成一个完整阶段后才推送 |
| 优点 | 用户感知「实时」，体验流畅 | 实现简单，减少 WebSocket 风暴 |
| 缺点 | 大量 Agent 并行时推送压力大；中间 token 无意义 | 用户等待时间更长，焦虑感增加 |
| **推荐** | **混合策略**：任务开始/结束/关键里程碑实时推送，中间 token 聚合后批量推送，每 5s 一次心跳保活。 |

#### 权衡 2：冲突检测位置（前端 vs 后端 vs 混合）

| 方案 | 纯前端 | 纯后端 | 混合（推荐） |
|---|---|---|---|
| 描述 | 前端拉取各 Agent 输出做 diff | 后端统一做语义 diff | 后端做 AST 级别的精确 diff，前端做文本级别的快速 diff |
| 优点 | 实时性强，改动快 | 结果准确，缓存可复用 | 后端产精确结果，前端提供即时反馈 |
| 缺点 | 浏览器处理大文件时性能差 | 实现成本高，延迟增加 | 两端都要维护逻辑 |
| **推荐** | **混合**：后端负责语义级冲突检测，前端负责展示级 diff 高亮。后端异步计算后推送冲突标记，前端先展示「检测中」状态。 |

#### 权衡 3：导出格式与粒度

| 方案 | 全量导出 | 摘要导出 | 自定义导出（推荐分阶段） |
|---|---|---|---|
| 描述 | 导出所有 Agent 的完整日志和推理链路 | 只导出结论和冲突标记 | 用户选择导出层级和内容 |
| 优点 | 信息完整，无遗漏 | 文件小，可读性强 | 灵活，适应多场景 |
| 缺点 | 文件巨大（>50MB 常见），用户读不完 | 可能遗漏关键推理步骤 | 实现复杂度高 |
| **推荐** | **V1 摘要导出 → V2 可展开层级导出 → V3 自定义模板** |

#### 权衡 4：协作空间生命周期

| 方案 | 与会话绑定 | 独立持久化（推荐） |
|---|---|---|
| 描述 | 主会话结束时协作空间一起销毁 | 协作空间独立于会话，可存档/回顾 |
| 理由 | 协作空间是重要的决策记录，即使会话结束，对比过程和结论仍有存档价值 |
| **推荐** | **独立持久化**，与 `task_sessions` 的墓碑模式一致 |

### 5. 实施路线图

#### RICE 优先级排序

| 功能 | Reach | Impact | Confidence | Effort | RICE Score |
|---|---|---|---|---|---|
| 导出报告 | 3 | 3 | 4 | 1 | 36.0 |
| 基础协作空间 + 实时状态 | 4 | 5 | 4 | 3 | 26.7 |
| 任务分解树视图 | 3 | 4 | 4 | 2 | 24.0 |
| 冲突检测（AST 级别） | 3 | 5 | 3 | 5 | 9.0 |
| 时间线视图 | 2 | 3 | 3 | 2 | 9.0 |
| 标注与评论 | 2 | 3 | 3 | 2 | 9.0 |

**评分说明**：
- 导出报告 Effort 小（1）却覆盖三类用户，RICE 最高，但依赖前置数据，放在 NEXT
- 冲突检测 Effort 大（5），但 P1 用户明确要求且是差异化亮点，值得投入

#### 路线图

```
NOW（2-3 周）—— 基础能力
├── US-01: 协作空间自动创建 + Agent 面板实时状态（WebSocket）
├── US-03 子集: 基础标注功能（纯文本评论）
├── 技术基建: 协作空间数据模型设计 + 事件流存储
└── [决策] 采用混合实时同步策略
    Effort: 2 后端 + 1 前端 = 3 人周

NEXT（2-3 周）—— 视图与交互
├── US-02: 任务分解树视图（V1）
├── US-04: 冲突检测 V1（基于文本 diff，非 AST）
├── 技术基建: 冲突标记数据模型 + 推送协议
└── [决策] 冲突检测先做文本级，AST 级放 LATER
    Effort: 2 后端 + 1 前端 = 3 人周

LATER（4-5 周）—— 深度与延展
├── US-02: 时间线视图
├── US-04 升级: AST 级别语义冲突检测
├── US-05: 导出报告（Markdown + PDF）
├── US-03 升级: 富文本标注 + @提及多人
└── 性能优化: 8 Agent 面板并发压力测试
    Effort: 3 后端 + 2 前端 = 5 人周
```

#### 风险与缓解

| 风险 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|
| WebSocket 在 8+ Agent 并发时推送风暴 | 中 | 高 | 限流、聚合推送、心跳降级 |
| 冲突检测误报率过高 | 中 | 中 | V1 先做文本级，用户可手动标记「误报」来训练模型 |
| 协作空间持久化导致存储膨胀 | 低 | 中 | 定期归档 + 用户可配置保留期 |
| 用户对「协作空间」概念理解成本高 | 中 | 中 | 随分解任务自动创建，零配置；内置引导 Tooltip |

### 总结

**核心设计理念**：协作空间不是独立功能，而是 Agent 并行工作模式的**自然可视化呈现**。用户不需要额外学习如何「创建协作空间」——它在 Coordinator 分解任务时自动生成，在任务完成时自动生成摘要报告。整个设计围绕「降低认知负荷」展开，让用户从「手动拼图」变为「自动组装」。

**明确不做的事**：
- 不在 V1 做实时协同编辑（多个用户同时操作一个空间）
- 不在 V1 做 Agent 之间的直接通信（Agent 仍通过 Coordinator 协调）
- 不使用 WebRTC 等复杂实时协议（WebSocket 足够）
- 不改变现有 Agent 的执行模型（协作空间是纯展示层）
