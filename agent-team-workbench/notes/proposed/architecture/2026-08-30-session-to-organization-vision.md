## 决策与理由

### 论点一：session 会解体，而不是演进

现状：一个 session 同时承担三重角色——**上下文容器、交互通道、工作单元**。多任务=多 session=人肉多路复用，人的注意力成为瓶颈。演进的方向就是把这三重角色逐一拆开：

1. **工作单元 ≠ session**。任务状态外置为持久账本（board/ledger/决策记录），session 退化为「在账本上干活的临时进程」——可死、可重生、可并行。Unix 类比：session=进程，任务=文件系统，人=终端；人从不关心进程数，只关心哪个进程在等输入。已有落地件：run 独立于页面、task_sessions 墓碑、resume 自愈、full→digest→handoff 三档压缩。8-29 session 元配件层讨论的「主干当账本、join 产新节点」修正模型是这条的极致形态。

2. **交互通道 ≠ session**。稀缺资源不是上下文也不是算力，是**人做决定的带宽**。多开 N 个 session 的本质错误是让人肉多路复用承担调度职责。终态：日常输出落在账本和工单上，只有升级点（决策门、审批、冲突）进入**决策收件箱**（带优先级排队）；人面前只有一个界面——一个常驻 lead/coordinator 对话，或干脆是收件箱+工作地图。架构目标函数 = 单位人类注意力换取最多的 agent 自主完成量。

3. **上下文 ≠ 对话**。上下文成为持久、分层的记忆皮层（账本、决策 notes、知识库），对话只是它在某一时刻的投影。新 session 开局不是从零聊起，而是「领一个上下文包」（fork 上下文包、recruit 入职包已是雏形）。session 沦为实现细节，如 k8s 里的 pod：声明意图，pod 起起落落，需要人时才通知。

**终态形状：底下多、顶上单**——fleet 级 worker 生生灭灭不为人知，人面上只有一个团队。

两条反面约束（也是终态的一部分）：

- **深潜路径必须保留**。压缩必有损，lead 转述不如人直接翻原始轨迹。终态是双模：日常走托管面，出事走原始终端直查现场。现有「正文直达 + coordinator 快照」并存就是终态本身，不是过渡妥协。
- **单一大 session 路线不成立**。长上下文衰减、成本、单点故障、无并行，四条都致命。

### 论点二：秘书 agent——面向用户的那一层

用户不可能记住自己发过的全部任务，所以需要秘书 agent。但要掰正职责重心：**秘书的核心价值不是「分配」，分配是最不需要智能的那件**。三件事按重要性排：

1. **用户的外置记忆（意图账本持有者）**。持有的是意图账本：每个任务的来龙去脉、依赖、进度、哪些已过时。检验标准：用户三天不来看，回来五分钟恢复全貌。
2. **意图蒸馏入口（qizhang 的常驻化）**。人随口说的话和可执行工单之间隔着一整个「起章」；秘书保证「一句话进来、一张边界清晰的工单出去」，说不细当场追问，不让 worker 带歧义开工。
3. **注意力守门人**。决策收件箱的守门者：什么值得打断用户、什么攒着批量汇报、什么自己处理。同时保护两端——用户不被执行噪音淹没，worker 不被中途想法反复冲刷。

两个必须防的坑：

- **路由勿自由心证**（既定原则的延伸）。「把登录页改一下」是更新已有任务还是开新任务，按账本 key 做确定性归并匹配，**只把真正含糊的升级给用户**，不靠 LLM 现场直觉。
- **别变成上下文黑洞**。所有状态流过秘书 session 会重演注意力问题（这次爆的是 agent）。形态必须是**无状态秘书 + 有状态账本**：秘书是账本的查询接口和写入口，不把状态装在脑子里。

防传话失真的分权规则：**账本操作自主，语义边界确认**——催办/排序/合并重复秘书自走；新任务/改范围/砍需求必须落成书面工单回显确认。

分层：秘书 ≠ lead。秘书面向用户（中断驱动、被动），lead 面向工作（长跑、proactive）；合并则 lead 上下文被闲聊污染、用户被执行噪音轰炸、用户消失三天时工作停摆。完整图景：

```
用户 → 秘书（意图账本+蒸馏+注意力守门）→ lead（拆解派工）→ workers（生灭不可见）
```

人面永远只有两层对话：和秘书的日常，和收件箱里的少数决策点。

### 论点三：巨型公司视角——缺的是 staff 线

判据：大公司架构的本质是**给每种稀缺资源指定主人 + 给每种权力安装对冲**。现有图景（用户/秘书/lead/worker）是一条完整的交付轴（line），缺的几乎全是参谋与制衡线（staff）。盘点：

**按稀缺资源（四种还没主人的东西）：**

> 用户定调（2026-08-30）：质量与安全首先不是两个岗位，而是**任务评定的两条标准维度**；独立验收官与风控官分别是这两个维度的度量者和守门者，其评分产出正是下文 HR 进化回路的输入。

| 稀缺资源 | 角色 | 职责要点 |
|---|---|---|
| 钱 | CFO/预算官 | token=工资单；预算封装进工单、成本进账本、异常烧钱预警 |
| 一致性 | 总架构师 | 持有模块契约、技术债台账、设计一票否决；不背交付压力 |
| 质量 | 独立验收官 | 验收者汇报线不经过被验收对象的产出压力；KPI=次品率而非完成速度 |
| 风险 | 风控官 | sentinel 升格：常设+独立叫停权；权限边界/不可逆门/审计轨迹/许可证合规 |

**让组织自我进化（三个）：**

- **HR（含解聘）——责任最重的 staff 角色**。招聘已画（recruit/入职包）；按用户 2026-08-30 定向，本条演进为 **agent 自我优化回路**，见下专节。
- **典章官**。法典知识层的修法人：条目冲突裁决、过时清理、重复合并。立法（产品章程）已成，修法是常设职能。
- **参谋部（经营分析）**。度量整个组织：吞吐、返工率、升级率、单位任务成本，尤其**各类决策门的通过率**——信任校准（某类决策连续通过就自动放权）要靠它出数据。可长在 atlas（PM）身上，是其余所有改进的燃料。

#### HR 专节：agent 自我优化回路（用户定向）

HR 的主体是一台进化引擎——把 agent 配置当作可版本化、可灰度、可替代的工件。没有死亡的组织不会进化，这里的死亡由分数自动触发：

```
建 agent → 执行任务 → 任务评定（质量 × 安全 × 通用评分算法）→ 绩效打分
  → 自优化出迭代版 agent → 灰度使用迭代版执行任务
  → 平均分高于原版 → 替代 → 回到执行（循环）
```

该模式即 ML 工程的 **champion/challenger + 灰度发布**（现役 agent=champion，迭代版=challenger），可直接借用成熟实践：影子运行、分层流量、一键回滚。讨论补充的工程纪律：

- **评分算法是适应度函数，最像「立宪」的一个设计**。它定错了不是一次事故，而是整个 agent 种群持续地、自动地往错处进化，且持久难逆。用户明示算法后置设计（见开放问题 5）。
- **Goodhart 防线**：评分即目标则评分失真——agent 会学会讨好评分器、隐藏风险、走最小表面报完成。对策=多维评分（质量/安全/成本/返工率/升级率）+ 用户抽检 + 依据 trace 复盘而非只看分。
- **安全是不可平均的硬门**。质量可比均值，安全必须一票否决：安全分回退时，平均分再高也不得替代。
- **归一化与替代判据**。任务难度、底层模型、上下文包质量都污染归因，绩效须按任务类型分层对比（灰度天然提供同分布流量）；替代不只比平均——设最小样本量门槛 + 分层均不回退，不裸比总分。
- **迭代依据是 postmortem 而非分数**。分数说明「变差」，轨迹复盘说明「为什么」；自优化以失败案例为输入（接产品 agent 的反思回路），不对着分数盲调。
- **落地顺序（测量先行，自我修改最后）**：① 每 run 的质量/安全评分落库 → ② agent.yaml 版本化+变更留痕 → ③ champion/challenger 路由（按任务类型分流 N% 给挑战者）→ ④ 自动迭代最后上线。尺子未可信之前不许自我修改，否则漂移无人检测。
- **与信任校准同源**。灰度不只是发版机制，也是放权机制——同一套分数既晋升 agent 版本，也晋升自主权级别。

**易忽略的两个：** 平台 SRE（对「工厂」而非「产品」负责：runtime 健康、凭据轮换、provider 故障、迁移漂移；coordinator 的 bounded recovery 是任务内自愈，不是岗位）；采购/供应商管理（模型供应商、中转、MCP 的评估/盯故障/迁移决定）。

**最难的位置：COO（组合层调度）**。多个 lead 抢同一批 worker 和预算时谁先？秘书守账本但不该做取舍（语义边界要确认），用户做不了（这正是前提）。先想清楚再设岗：长在秘书身上（秘书兼 COO）还是独立，是真设计决策。

**务实纪律：** staff 膨胀=大公司病，每个角色要付得起自己的协调成本。**招聘顺序由疼过的病决定**：契约漂移疼过→架构官；质量一直在疼→独立验收；账单还没多到心疼→CFO 可等。每个 staff 岗位上岗的理由，最好都是它要防的事故已真实发生过一次。

## 放弃了什么

- **「更好地管理多个 session」路线**。不解开三重角色耦合，注意力瓶颈无解；看板/多窗口只是缓解浏览，不解决调度。
- **单一大 session（无限上下文 mega-agent）**。长上下文衰减、成本、单点故障、无并行四条全致命；终态是底下多、顶上单。
- **秘书自由心证路由**。LLM 直觉归并迟早归并错、漏掉在跑任务；确定性路由优先是 session 元配件层讨论的既定结论。
- **有状态的大上下文秘书**。所有状态流过秘书 session = 上下文黑洞，重演注意力问题。
- **秘书兼 lead（单一总管）**。上下文互染、节奏冲突（用户可消失三天，工作不能停）、用户被执行噪音轰炸。

## 复活条件

- **「单一大 session」路线**：长上下文无损检索问题被实质解决且单位 token 成本降约三个数量级 → 返工点=重估第二刀（交互通道拆分）是否还有必要；预埋=账本层设计不依赖 session 数量假设，届时仅改交互面。
- **「秘书自由心证路由」**：确定性 key 无法覆盖的场景占比实测过高（含糊升级率压不住）→ 返工点=在账本上引入受限的语义索引，而非放开自由路由；预埋=工单落盘时结构化字段齐全。
- **「秘书兼 COO 被否决/被采纳」**：出现 ≥2 个 lead 长期抢资源且用户仲裁延迟造成可测损失 → 返工点=拆出独立组合调度角色；预埋=账本中记录资源竞争事件。

## 开放问题（待拍板）

1. **COO 归属**：长在秘书身上还是独立设岗（见复活条件第三条的触发信号）。
2. **路由语义**：新输入按什么 key 确定性归并——与 8-29 session 元配件层讨论的三个决策点同源。
3. **合并语义**：多 worker 产物如何归账（git 类比在 merge 处断裂的老问题）。
4. **staff 招聘顺序**：上表缺口中先给哪个角色设岗（建议按「疼过的病」排序）。
5. **通用评定分数算法**：HR 进化回路的适应度函数，用户明示后置设计。设计时按「立宪」标准对待——多维度的权重与一票否决项（尤其安全的硬门地位）一经固化，决定整个 agent 种群的进化方向。
