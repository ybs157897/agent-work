# Agent 自建与自治（画框）终局草案：嵌套编排域 + recruit 词汇 + 无 MCP 终局

Status: proposed（讨论进行中，未定稿；实现细节与架构设计后续专题讨论）

讨论时间线：2026-08-27 与用户对谈沉淀（辅助会话起草）；同日主线会话两轮补充
（Cordis 分界/表达力阶梯/空间数据面/残余风险/分期演进/备选与否决；Tiangong
对照/旗舰团队日循环/产品 agent 蓝图/路线定调）。
三个话题拼的是同一个东西的三个面——
**招聘**（框里的 agent 从哪来）、**运转**（框怎么自治）、**经济**（框花谁的钱、归谁管）。

## 路线定调（防跑偏锚点，2026-08-27 用户定调）

**现阶段唯一焦点：把既有 agent 的能力做扎实**——看板主循环跑顺（发布→认领→
派工→交付→验收全链路的体验缺口补齐）+ 第一个专职 agent（产品 agent）的自维护
回路落地。画框/recruit/自组装是已定调的远期方向（本文主体为其设计契约），
**方向先定死，实现顺序不抢跑**。

防跑偏检查（每次排期前自问）：

1. 这件事让哪个**既有 agent** 变强了？答不上来 → 属画框层，延后；
2. 这件事要动词汇表/状态机/引擎吗？是 → 先对照文末负向保证，能不动就不动；
3. 远期设计只允许以"不返工"的方式影响近期实现——预留字段、遵守契约，
   不做提前实现。

## 旗舰团队与日循环（宿主场景）

方向分野：同类项目 Tiangong 造的是"流程"（固定名册跑软件交付流水线），本项目
造的是"组织"——**主 agent 是大脑，codex/kimi CLI 等是各 agent 的核心引擎**，
用这些引擎拼出为用户服务的旗舰团队。用户不常聊天，主要交互面是任务看板。

日循环全景（看板主循环 = 白天，自维护回路 = 夜里）：

```
早上：用户往看板写任务（不聊天）
白天：主 agent 认领→规划→派工→workers 执行→lead 评估
傍晚：任务进待验收，lead 敲门（到货通知），用户验收收货
夜里：产品 agent 生物钟启动——梳理当天任务产出，补全知识库
```

看板主循环逐环节对账（全部已有座位，缺口在体验层）：

| 环节 | 现有机制 | 状态 |
|---|---|---|
| 用户写看板 | work_items 看板 + 发布面 | ✅ |
| 主 agent 领取 | 认领模式 + F1 执行锁；assignment 触发源 | ✅ |
| 规划分配 | lead planner → plan 提取 → 子任务树派工 | ✅ |
| 执行 | worker runs；子树 lead 可嵌套 | ✅ |
| 汇报 | run 终态 + artifacts 回流 + 静默钩子唤醒 owner | ✅ |
| 评估交用户 | acceptance 评估 → acceptance 相位 | ✅ |
| 用户验收 | Accept() 唯一收口；返工走 chat + BeginExecution 打回 | ✅ |

体验层三缺口（近期要补的"最后一公里"）：

1. **到货通知**：任务进 acceptance 相位时主动敲门（SSE 事件已有，缺推送/汇总/
   日报形态）——用户不聊天的前提是 agent 会来敲门，否则他得自己盯板；
2. **验收摘要**：交给用户的是 lead 产出的交付摘要（做了什么/怎么验/风险在哪），
   不是 artifact 清单；
3. **自动起跑**：发布 todo → lead 自动认领的链路机制在（assignment 源），认领
   与派工模型的关系见未决问题。

## 产品 agent 自维护回路（第一个专职 agent 蓝图）

旗舰团队第一名正式成员 = **会自己长大的专家**。四个部件全部是现有件 + 草案件
的组装，无新架构：

| 部件 | 需求 | 现有 | 缺口 |
|---|---|---|---|
| 生物钟 | 定时梳理知识文档 | scheduling timer 源 + agent_wakeup_requests + coalescing | agent.yaml 声明式 `schedules` 字段（cron → 定时入队 → 建 run） |
| 反思回路 | 任务结束时补全涉及自己且文档缺失的内容 | run 终态触发源 + 静默钩子先例（maybeAdvancePlans） | grooming plan 模板 + "自身 run 终态"触发器声明（习惯=数据，不改引擎） |
| 记忆皮层 | 固定路径存放好维护 | knowledge/ 文件知识层 + frontmatter + consult_knowledge | per-agent 命名空间约定（knowledge/product/）+ 写入纪律（走 git/notes 文化，不开第二通道） |
| 工具手 | 代码逻辑（盘点脚本等） | 框内 go run（今日即有） | 框内 go build 常驻工具（依赖空间数据面，远期章节） |

最小落地路径：`schedules` 声明字段 → grooming plan 模板 → `knowledge/<domain>/`
约定 → 盘点脚本（先 go run 一次性，够用再常驻）。与产品章程
（docs/product-agent-charter.md，P0 system_prompt 链路已验证）衔接：章程定
"他是谁"，本回路定"他怎么每天变强"。

## 愿景一句话

主体 agent 在运行中意识到某类任务对该用户高频出现，遂"画框"创建一个专职 agent
（包工头）：入职包由创建者起草（提示词/app-server 选择/模型配置/业务资产），框内
完全自治（可给自己写 Go 工具、可修订自己的提示词与模板），对外只暴露
dispatch/acceptance 契约——"我调用你，内部如何实现我不管，交付一个结果"。

## 核心模型三层

### 1. 框的本质 = 一棵子树（不是技术容器）

"框内随便写代码自己弄"不需要新机制——agent 在 harness 会话里写代码、跑代码是
执行面的日常。框 = **一块空间 + 一份预算 + 一个契约 + 一条谱系**。控制平面永远
不读框内、不热载框内代码（进程边界即沙箱边界）。

### 2. 包工头 = 子树内的 lead（模式可递归）

现架构的 lead 模式就是包工头模式：认领→规划（plan 5 动词）→派工（子任务树
parent_id）→评估（acceptance criteria）→返工（defer/join/supersede）→交付。
缺口不是新层，是**把 lead 从顶层专属推广到任意子树可嵌套**，配递归深度上限。

关键抉择（已定向）：框 agent "调 codex"的方式是产出 dispatch 动词由控制平面
代起 run（**经控制平面递归**），绝不框内直连 app-server 自管进程——后者等于
每个框长一个模型手搓的迷你控制平面，13 态状态机/resume 纪律/取消/审计全部失控。

### 3. 经济 = 预算信封 + 谱系 + 配额

- agents 加 `created_by` 谱系（work_items parent_id 先例）；
- 预算信封：usage 按 lineage 聚合，agent 级累计预算，超限框冻结（落 blocker
  不杀数据）；
- 创建配额 + 递归深度上限（防套娃）；
- 权限降级继承：自建 agent 权限 ≤ 父。

## 入职包（agent bundle）目录契约

招聘的产物不是一条配置，是一个完整目录：

```
agents/<slug>/
  agent.yaml            # 四轴：runtime(preferred/fallbacks/mode) + model ref + 权限 + approval_policy
  prompt.md             # 角色提示词（创建者起草）
  onboarding/           # 业务资产区（新增）
    plan-templates/     # 任务规划模板（如"开发者的任务规划"实例）
    thinking/           # 方法论资产（如"架构 agent 的架构设计思维图"）
    examples/           # 示例实例（few-shot 种子）
    knowledge.md        # 种子知识 / workspace 知识库引用清单
```

注入点唯一：onboarding 资产经 orchestrator 快照进 run.Input 或经
consult_knowledge 检索，无第二条私设通道——快照纪律（目录可变、运行不可变）
自动覆盖业务资产。

### 框的空间数据面（入职包之外的"一块空间"具体化）

框内 agent 自己的生产区与入职包分立，落 **agent 空间目录**（如
`.agent-work/spaces/<slug>/`）：

- 框内 scratch、`go build` 产物、自建工具全在此；配磁盘/文件数配额；
- **对外唯一出口 = artifact 通道**（版本化 + 幂等 + 审计），空间本身不出框；
- 控制平面不读空间内容（黑盒），仅保留安全扫描钩子位（供应链护栏的执行点）；
- 与 onboarding/ 的分界：onboarding 是创建者写的入职资产（进 run.Input 快照，
  目录可变运行不可变）；spaces 是框内 agent 的生产区（不进快照，随时可变，
  随 archive 冻结）。

## 创建生命周期六环节

1. **意识**：任务模式频次信号（最弱一环；从同类 dispatch 计数/用户明示起步，
   远期做聚类面板）；
2. **起草**：创建者产出入职包草稿。runtime/模型选择有据可依——AdapterManifest
   能力矩阵与模型注册表（context_window）都是机器可读目录；
3. **评审**：草稿作为 artifact 走审批钩子（ApprovalRequest 复用，首期全人审，
   后按风险分级）；
4. **入职**：批准后 Importer 投影、指纹注册、立即可 dispatch（现有机制零新增）；
5. **试用**：前 N 次派工的 acceptance 通过率/成本/返工记账（usage 聚合到
   agent 维度）；不达标反馈创建者修订入职包——ConfigDigest 指纹规则自动强制
   新会话，自我改进循环的安全底座已存在；
6. **转正/解雇**：高频达标→常驻；低频超标→archive（墓碑停用）。招聘解雇对称、
   皆有审计。

## 无 MCP 终局（用户明确约束）

**终局不存在 MCP，也不是本项目范畴；不承诺任何工具协议兼容性（负向保证）。**

接口总数封闭为四条：

1. agent → 控制平面：**plan 词汇表**（出谋唯一通道）；
2. 控制平面 → agent：**dispatch + acceptance 契约**；
3. agent ↔ agent：**artifact 中转**（经审计）；
4. agent 内部：框内文件与二进制，纯私事。

由此替代原 MCP 挂点的两个设计：

- **创建写面 → `recruit` 词汇动词**：lead 在 plan 围栏里写
  `recruit(slug, bundle: artifact_ref, purpose)`；plan_extract 提取 → schema
  校验 → 审批 → Importer 实例化。词汇表 5→6 动词是一次正经 contracts 版本化
  变更，比旁开工具口更合"Agent 出谋，控制平面执政"。另配 `retire`（对称解雇）。
- **能力共享 → 能力即 agent / 产物即文件**：复用能力 = dispatch 给拥有它的
  agent（包工头递归）；或二进制+用法说明作为版本化 artifact 入共享区，消费方
  harness 直接 exec。发现机制 = 知识层（工具即知识条目），无注册中心、无协议层。

## agent 写 Go 代码的三条去处（全部无协议）

1. 一次性计算：框内 `go run` 拿输出（今日即有）；
2. 框内常驻工具：`go build` 产物存自己空间，harness 反复 exec；取消/超时/资源
   走执行面子进程管理（pgid 现成）；
3. 跨框共享：见上（能力即 agent / 产物即文件）。

共同点：Go 代码永远活在子进程里，从不进控制平面进程。编译型语言这个最不利
情况都无热加载地接住，架构对"agent 写代码"的容纳度即完备。

护栏：构建供应链（框内 vendored 模块/内部 GOPROXY，go.sum 变更进审批）；
源码+二进制（记 digest）一起 artifact 版本化；二进制无凭据，能摸到什么由框的
权限信封决定。

## 表达力阶梯与两把锁

框内逻辑的表达力阶梯（从低到高，逐级启用，不跳级）：

1. **plan 模板**（纯数据）：覆盖八成"固定流程复用"需求，零新增攻击面；
2. **框内脚本/二进制**（子进程）：执行面日常，见上节三条去处；
3. **沙箱决策函数**（仅当需程序化策略，如 continue/new_topic 判定、子任务拆分
   启发式）：Starlark（首选，确定性）/ expr / wazero(WASM)。输入=自己子树上下文
   快照，输出=动词序列，照常过执行器校验；
4. **引擎热载**：❌ 永不（负向保证 #2）。

启用第 3 级时的两把锁，缺一即漏：

- 锁 1 执行隔离：解释器/WASM 无 I/O 无网络、可限时限量；
- 锁 2 权限隔离：作用域钉死自己子树、预算切块、降级继承、随父生命周期。
  沙箱不替代护栏，只在护栏内嵌套——沙箱代码只能"出动词"，执法永远归执行器。

## 与 Cordis 的分界（决策锚点，本讨论的起点）

对照 cordiverse/cordis（DSH 底层 TS 插件框架）：两者都谈"可组合性"，但**组合
维度不同——Cordis 组件化的对象是代码（Service/插件：进程内、确定性、无意志）；
本项目组件化的对象是 agent（进程外、有主权、会思考的智能单元）**。这是定性
分界，机制差异全部由此派生：

| 维度 | Cordis（代码组件化） | 本项目（agent 组件化） |
|---|---|---|
| 组合单元 | Service 插件（代码对象） | agent（四轴配置=数据，创建即用） |
| 接口语义 | 函数签名/类型——编译期契约 | 任务契约（subtask+acceptance）——运行期验收、可返工 |
| 失败模型 | 异常/错误码，调用方处理 | run 状态机终态 + blocker + 返工循环 |
| 组装者 | 开发者（cordis.yml 静态声明） | agent 自己（运行时 recruit，组装是涌现的） |
| 组件自我性 | 不会拒绝调用、不自改（改=开发者改） | 可经 approval 拒、可自改入职包、可成长（试用→转正） |
| 复用经济学 | 调用零边际成本，无需经济学 | dispatch 花 token——高频意识/试用期/转正解雇即组件生命周期管理 |

两个推论：

1. **组件可自组装**：插件不会自己决定"再装一个插件"；agent 组件化的核心新性质
   恰恰是组装者本身是 agent（recruit 的发起者）——代码组件世界不存在的能力；
2. **两层组合不冲突**：agent **之间**的组合归控制平面（本设计）；agent **内部**
   的组合是框内私事——dsh 框内自己就跑着 cordis（终局接口第 4 条已预留此分界）。

另有两条机制分界：**热载只发生在执行面**（Cordis 热载进 harness，我们同构经
dsh adapter 今日已有；编排器永不热载——不是 Go 做不到，是任何语言都不该开，
引擎语义被模型改写=护栏失效）；**失败哲学相反**（Cordis 可逆副作用的 reload
世界 vs 本项目不可逆审计：墓碑/终态唯一/任何 Outcome 必落终态）。

结论：借鉴其概念（事件契约化、注册可逆），不依赖其实现（API 自认未稳定）。

## 与 Tiangong 的对照（cynos-ai/Tiangong，可学与不学）

同构多 agent 编排项目（1 Leader + 5 静态成员，AgentTeams 内核，evidence-backed
纪律）。方向分野见"旗舰团队与日循环"节——它造流程，本项目造组织。代码层核实
结论（非 README 自述）：

**可学（五点）**：

1. **Leader 薄工具面 + 服务端执法**：Leader 全部能力 = 11 个 TypeBox schema
   工具（薄封装转发），零硬编码工作流——决策顺序 100% 归模型，守卫全在服务端
   （CloseGuard）。验证了 recruit 路线：主 agent 带团队不需要代码编排逻辑；
2. **生命周期 hook 执法模式**：成员约束全挂在 before_prompt_build / agent_end
   两点——五重绑定校验（只许执行分给自己的 assigned 任务）、单会话独占、prompt
   强制注入权威 TaskSpec、输出截断兜底单次回写（乐观并发）。对标本项目 SPI
   Callbacks，是"任务结束自动沉淀"类回路的实现范式；
3. **聊天不构成授权**：审批只认认证 Human 对精确 Operation ID 的 approved/
   rejected 事件，任何聊天文本不算——值得钉进本项目审批面负向保证；
4. **CloseGuard 只核机器事实**：完成判定中"语义归 Leader、机器事实归系统"的
   显式分界，与本项目 acceptance 评估 + Accept 收口同构，可补这层显式声明；
5. **并行写者不同可写根**：空间数据面的同款实证，连动机都一致（防并行互踩）。

**不学**：报告型成员压缩——代码把成员的 toolResultRefs/deliverableRefs 硬编码
为空、报告截断 8KB，成员只能交一段文本。本项目成员是**交付型**（artifact 通道
+ acceptance 契约），信任分歧放在验收，不做表达力阉割。

**它明确不做的恰是本项目的远期**：agent 创建 agent、Skill 动态指派被划到其
初始产品边界之外——recruit 方向没有现成答案，站在它验证过的协作语义之上加
动态层即可。

## 残余风险与缓解（confinement 不自动解决什么）

- **作者被注入**：起草/修订入职包的 agent 本身可能被提示词注入操纵。缓解=
  confinement 本身——爆炸半径 = 子树 + 预算切块；外加入职包首期全人审；
- **共享资源间接全局效应**：provider 限流冲击、事件流噪音——预算信封配额 +
  事件按谱系命名空间隔离；
- **可观测性债**：生产中从此有 agent 写的代码/模板/提示词，必须版本化
  （artifact）+ 首用审批 + 可确定性回放（Starlark 首选的又一理由）；
- **意识误报**：频次信号是最弱一环，误报即 agent 增殖——创建配额与试用期
  不达标回退（archive）构成双向闸门。

## 分期演进（每期独立可用；顺序即防跑偏）

- **近期（把既有 agent 做强，现阶段唯一焦点）**：看板体验三缺口（到货通知 /
  验收摘要 / 自动起跑收口）+ 产品 agent 自维护回路（schedules 声明、grooming
  plan 模板、knowledge 命名空间约定、go run 盘点脚本）；
- **中期（画框一等化）**：`created_by` 谱系 + recruit/retire 词汇（contracts
  版本化）+ bundle schema + onboarding 目录约定（先约定后强制）；
- **远期（框成型）**：预算信封与 lineage 聚合、空间目录配额与 artifact 唯一
  出口、自改入职包闭环（审计事件 + 首改审批）、子树 lead 执行路径验证；
- **终局（框生态）**：意识信号自动化（dispatch 相似度聚类）、按风险分级免审、
  atw-mcp 退役与认领模式归并。

## 负向保证（钉死，不随实现讨论松动）

1. 词汇表封闭；扩张只经 contracts 版本化（recruit/retire 亦然）；
2. 控制平面不热载、不解释、不理解任何 agent 代码；agent 代码只活在子进程；
3. 框再自治，进出必走 run 状态机与审计——不留暗门；
4. 权限降级继承，自建 agent 永不越权于创建者；
5. 无 MCP、无工具协议、无注册中心（终局接口四条封闭）；
6. 墓碑纪律延伸：agent 停用不物理删（archive），谱系可追溯。

## 已登记的迁移问题（到时先改 end-goal 再动代码）

1. **atw-mcp（F5）退役路径**：现 task_claim/task_return 支撑认领模式；终局无
   MCP 意味着认领要么动词化、要么被直接派工模型吸收；
2. **agent 维度 usage 聚合**："意识"自动化的前提，也是预算信封的数据面。

## 备选与否决（决策留痕）

- **MCP agent_create/agent_archive 写面**（主线初案）：被 recruit/retire 词汇
  取代——工具写面绕过 plan 围栏与 schema 校验，词汇化让创建与其他动词共用同一
  护栏/审批/审计骨架，且与无 MCP 终局自洽；
- **能力注册中心 / 工具协议层**（主线远期初案）：被"能力即 agent、产物即文件、
  知识层发现"取代——少一层常驻设施，发现退化为检索问题；
- **框内直连 app-server 自管进程**：正文核心模型已述（迷你控制平面失控），否决；
- **引擎热载 / 进程内解释框内代码**：负向保证 #2 钉死。
