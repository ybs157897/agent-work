# 模型删除导致注册表损坏

Status: implemented

## 证据与决策

预览实例删除模型后，`/api/v1/models` 返回 500，日志为 `registry.yaml: yaml: line 52: could not find expected ':'`；健康检查、Agent 列表和知识配置仍为 200。现场注册表末尾多出单独的 `ash`，原文件已保存到实例目录供对照。

`web/src/pages/models.page.tsx` 删除供应商时并发删除旗下模型；`internal/modelconfig` 的读、改、写没有串行化，原子写又复用了固定的 `.tmp` 路径。并发写可能复用同一 inode，破坏最终 YAML；即使仅改为唯一临时文件，也会留下覆盖其他成功变更的问题。

修复在存储层完整串行化同一路径的读改写，并用独立临时文件替换目标。共享同一写入函数的凭据存储一并核对，保留 0600 权限。恢复现场时保留用户新建的供应商及模型，不用初始模板覆盖当前注册表。

HTTP 幂等回执确认 DeepSeek 供应商的两条删除请求发生在同一毫秒：`deepseek-v4-flash` 返回 204，但仍留在最终文件中；`deepseek-v4-pro` 返回 422，原因是固定临时文件 rename 时已不存在。现场修复只移除了无效尾行，保留当前有效条目，包括用户新建的 `glm-5-3-flash`。

## 放弃了什么

- 不通过前端逐条删除掩盖服务端并发错误。
- 不把解析失败当成空注册表，以免误导用户或覆盖有效配置。
- 不仅处理临时文件名，而忽略读改写丢更新。
- 不在这次故障修复中改变“删除已引用模型后，新 Run 明确报缺少模型”的既有 API 语义，也不自动替用户更换 Agent 模型。

## 验证边界

并发删除不同模型后，所有成功删除都应生效，读取始终得到合法完整 YAML；并发新增/更新模型和凭据不得丢失其他成功变更。同一路径的多个存储实例也必须遵守同一写入顺序。

路径锁在单个控制面进程内共享，不是跨进程文件锁。读端仍读取同一个文件权威入口，唯一临时文件 + rename 保证只见完整旧版或新版。

验证：modelconfig 全包 normal/race/vet 通过，并重复 20 次；HTTP 并发删除、删除幂等及凭据触面 race 通过。用 Go overlay 在原实现上运行同一 HTTP 并发回归，可复现“所有请求成功但仍残留两个模型”，修复后全部删除且读端正常。`go build ./cmd/control-plane` 与 HTTP/modelconfig vet 通过。
