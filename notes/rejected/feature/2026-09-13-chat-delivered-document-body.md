# 对话交付型文档以正文承载

Status: rejected（2026-09-13 当天被用户否决并撤回）

## 为什么被否决

用户看到线上效果后明确否掉：「这应该用 md 渲染才对，现在直接是展示到正文里面去了」。把整篇文档摊进
消息正文，等于把 agent 的解释性正文和交付物糊在一起——文档没有独立形态、不能折叠、也没法和正文的
结论分层。替代方案见 [Run 文件只读预览](../../implemented/feature/2026-09-13-run-file-preview-drawer.md)：
文档照旧落盘，`file` 块给仓库相对路径，用户点开在抽屉里读渲染后的 Markdown。

## 当初怎么做的（已撤回）

`output_contract.go` 的 languagegui/v1 追加段要求「交付型文档必须在正文完整给出」，并收紧 file 块口径为
「只报告文件存在，不得用来把文档交给用户」；[ContentBlock v1](../../../docs/frontend/chat-content-blocks-v1.md)
同步写了「落盘与展示是两条通道，落盘不得替代正文」。该规则已被 2026-09-13 的第二刀替换成
「交付型文档用带 path 的 file 块指向」。

## 当初的起因（仍然成立）

一次真实会话里 Nova 把需求文档写成 `notes/proposed/feature/2026-09-13-taskboard-title-search.md` 并在任务
worktree 提交，对话正文只给了同名的 file 块指针，块的 `url` 是 `file:///Users/...`；前端安全 URL 白名单
（`isSafeContentUrl`）按规范丢弃非 http(s)/站内 URL，规范又规定「没有安全 URL 时只展示元数据，不渲染
假下载动作」，于是那行只剩文件名与大小，用户点不开也读不到。**问题是真的，只是解法错了。**

## 仍然成立的否决

- **只给「复制路径」**：改不动「读不到内容」这件事，只是让不可用的行看起来可用。
- **放开 `file://` URL**：浏览器禁止 http 页面跳转 `file://`，放开只会渲染一个点了没反应的假动作。
- **把文档塞进 block 的 JSON 字符串里整篇抄一遍**：长文档的转义风险会让整个 fence 解析失败，回落成源码；
  文件已经在盘上，没必要复制一份进消息。

## 复活条件

只有当「仓库里不能存在这份文档」（例如产出物必须只存在于对话、不落任何文件系统）时，才重新考虑正文承载；
那时应按当时的 UI 形态重新设计，而不是恢复本 note 描述的那套规则。
