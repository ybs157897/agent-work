## 执行摘要

```
产品路线图 - Agent Team Workbench 演进规划
=============================================
当前阶段：本地专家工具（工程骨架 B 78/100，产品缺位仍落后于实现速度）
业务目标：从可靠的单机控制面进化为可团队协作的 Agent 编排平台
```

**一句话判断**：当前最紧迫的不是「加更多能力」，而是「让已有能力可以被安全、可重复地交付」——CI 门禁、凭据安全、真实认证是进入下一阶段的三道闸门。

## 当前状态回顾

### 工程骨架强度（已越过原型期）

- 13 态 Run 状态机，终态不可逆，幂等/Outbox/乐观锁成熟
- 8 个 Runtime 适配器（Codex、Kimi、DSH、Claude Code、mock、scripted、zcode）
- 56 条 REST 路由，覆盖全链路：任务发布→计划→派工→执行→审批→验收
- 后端 358+ 测试，前端 447 测试，设计系统有语义 token 门禁
- 看板主循环 7 个环节全部在运行（发布→认领→规划→派工→执行→汇报→验收）

### 核心短板（按优先级排列）

| 短板 | 影响 | 等级 |
|------|------|------|
| CI workflow 完全缺失 | 每次合入依赖本机自觉，不可持续 | P0 |
| 凭据明文回显端点 | 部署环境变化即安全事件 | P0 |
| 认证为演示角色 | 多人使用时无权限控制 | P0 |
| 产品文档落后于实现 | 新成员无法判断完成度 | P1 |
| 用户概念负担高 | 6+ 层概念堆叠，无首次成功路径 | P1 |
| 应用层 God 对象（4928 行） | 变更波及全系统，阻碍迭代速度 | P1 |
| 工作区污染 | 混合改动不符合分刀提交纪律 | P1 |
| 缺少产品指标埋点 | 无法量化用户价值和迭代方向 | P2 |

## 关键决策

### 1. 产品 Agent 的「到货通知」形态

**决策：** 先浮标后通知中心。本次我们不建独立通知面板，而是在看板/任务列表使用 badge 和浮标（侵入小、1 天落地）。等用户验证了通知的消费频次和转化率，再决定是否扩展为独立通知系统。

### 2. `application` 包拆分时机

**决策：** NEXT 阶段同步做，不推迟。架构耦合评审已标注为 P0 —— 当前 Service 是 4928 行的 God 对象，每次新功能都改它，不改拆分的代价是每轮迭代的摩擦成本。配合阶段 1 补测试覆盖，把拆包风险控制到最低。

### 3. Agent 招聘 vs 看板主循环优先级

**决策：** 看板主循环体验（到货通知/验收摘要/自动起跑）优先于画框/recruit。用户已定调「现阶段唯一焦点是把既有 agent 的能力做扎实」。recruit 方向已设计好契约，但实现顺序不抢跑。分界线：看板三缺口补齐 + 产品 agent 自维护回路验证通过后，才启动 recruit 实现。

### 4. 前端技术栈收敛

**决策：** 不引入 Ant Design 或其他组件库。当前 Aceternity UI + 自主 Ink Design System 的路线已经验证了可维护性，且 ANTd 的引入会增加包体积和样式冲突风险。仅借 Ant Design X 的交互范式（ThoughtChain/Bubble/RICH）作为设计参考，不依赖其实现。

## 风险与缓解

### 高影响风险

| 风险 | 影响 | 概率 | 缓解 |
|------|------|------|------|
| CI 建立后现有测试在 CI 环境失败 | 阶段 1 延后 1-2 天 | 中 | 先本地模拟 CI 环境跑全量，预判失败点 |
| 真实身份认证设计复杂度超预期 | 阶段 1 延后 1 周 | 中 | 最小 MVP：JWT + 本地用户表，不依赖外部 IdP |
| `application` 拆分期间新增功能受阻 | 阶段 2 交付延迟 | 高 | 拆分期间只修 bug 不增功能，配合 Feature Flag 隔离 |
| 产品 Agent 首轮自维护 loop 产出质量低 | 用户信心下降 | 中 | 首轮人审 + 调整 prompt，逐步放开自动化 |

### 待验证假设

1. 目标用户愿意从 IDE/CLI 切换到 Workbench（未验证留存和使用频次）
2. Lead/Worker 编排能降低总交付时间（需 A/B 对比单人单 Agent 与多 Agent 编排）
3. 审批不会成为主要阻塞点（需统计等待时长、拒绝率和超时率）
4. 用户理解当前概念模型（建议对 5 名目标用户做首次成功路径测试）
5. SQLite 本地模式可以平滑迁到 PostgreSQL 团队模式（需一次真实迁移演练和并发压测）
6. 产品 Agent 的定时梳理产出对用户有价值（首轮跑完即验证）
